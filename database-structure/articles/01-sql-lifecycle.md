# 数据库的结构 01｜一条 SQL 语句，在数据库内部经历了什么？

我们每天都在使用数据库。

对于一个程序员来说，查询数据可能只需要写下一条 SQL。对于一个 DBA 来说，这样的语句更是再熟悉不过。

```sql
SELECT * FROM users WHERE id = 100;
```

按下回车，数据库返回一条记录。整个过程可能只需要几毫秒，甚至不到一毫秒。

看起来没有什么特别的。我们告诉数据库要找什么，它就把结果交给我们。

但如果仔细想想，这件事其实没有那么简单。

数据库首先需要理解我们写下的这段文字，判断它是否合法，确认表和字段是否存在，然后决定采用什么方法寻找数据。真正开始查询以后，它还需要访问内存或者磁盘，找到相应的数据页，从中定位记录，判断这条记录对当前事务是否可见，最后把结果返回给客户端。

这一切，都发生在一次看似简单的查询之中。

更有意思的是，同样一条 SQL，在不同时间执行，数据库内部采用的方法可能完全不同。有时使用索引，有时扫描整张表；有时只需要访问内存，有时却要等待磁盘读取。

为什么会这样？

如果我们想真正理解数据库，就需要从这条 SQL 开始，走进数据库内部，看看它究竟经历了什么。

## 一、数据库首先要理解你在说什么

我们先从最容易忽略的地方开始。

当 PostgreSQL 收到这条 SQL 时，它看到的并不是一个已经可以执行的操作，而是一段文本。

```sql
SELECT * FROM users WHERE id = 100;
```

对于计算机而言，`SELECT`、`FROM`、`WHERE` 最初都只是字符。数据库必须先判断这些字符是否符合 SQL 语言的规则。

这个过程叫作解析（Parsing）。

我们可以把它理解成阅读一句话。人看到“从用户表中找到编号为 100 的用户”，能够理解其中的意思，但计算机必须通过明确的语法规则，把这句话转换成内部可以处理的结构。

PostgreSQL 的解析器会识别 SQL 中的关键字、标识符、运算符和表达式，并建立一棵语法树。

所谓语法树，并没有想象中那么神秘。它只是把原来线性排列的文字，转换成具有层次关系的数据结构。

例如，我们可以把这条 SQL 的基本含义简化为：

- 这是一个 SELECT 查询。
- 查询对象是 users。
- 需要返回所有列。
- 筛选条件是 id 等于 100。

注意，这只是帮助理解的简化描述，并不是 PostgreSQL 真实语法树的完整结构。

完成初步语法解析，并不意味着数据库已经确认这条 SQL 可以执行。

假设我们写的是：

```sql
SELECT age FROM users;
```

语法本身没有问题，但如果 `users` 表中根本不存在 `age` 字段，数据库仍然无法执行。

因此，PostgreSQL 还需要进行语义分析。它会查询系统目录，确认表、列、数据类型和相关对象，解析名称引用，并检查相应权限。

在 PostgreSQL 的内部处理流程中，原始语法解析之后还会经过分析与查询重写阶段。查询重写可以处理视图以及规则系统定义的某些转换。

经过这些步骤，一条原本只是文本的 SQL，才逐渐变成数据库内部能够理解的查询结构。

但到这里，数据库仍然没有真正开始读取用户数据。

因为还有一个更重要的问题没有解决。

**它知道我们要找什么，却还没有决定应该怎样找。**

## 二、同样一条 SQL，为什么会有不同的执行方法？

假设 `users` 表只有 100 条记录。

我们要找到 `id = 100` 的用户，最直接的办法就是从第一条开始，一条一条检查，直到找到目标。

这种方法叫作顺序扫描（Sequential Scan）。

如果表只有几十条或者几百条记录，顺序扫描可能非常高效。因为读取少量连续的数据页，往往比额外访问索引更简单。

但如果表有一亿条记录呢？

显然，我们不希望每次查询都从头到尾检查一亿条数据。

这时候，索引就有了价值。

可以把索引暂时理解为一本书的目录。我们不需要翻遍整本书，只需要先找到目录中的位置，再进入对应的页面。

对于 PostgreSQL 常见的 B-Tree 索引来说，数据库可以沿着树形结构逐层查找，快速定位可能包含目标记录的位置。

于是，同样一条 SQL，就有了至少两种可能的执行方式：

一种是扫描整张表，另一种是通过索引定位数据。

究竟选择哪一种？

很多刚接触数据库内部原理的读者，可能会认为，只要建立了索引，数据库就应该使用索引。

实际上并不是这样。

数据库优化器关心的不是有没有索引，而是**哪一种执行方式的预计成本更低**。

如果表很小，顺序扫描可能更便宜。如果查询需要返回表中绝大多数记录，即使存在索引，顺序扫描也可能更合适。

反过来，如果表非常大，而查询只返回极少量记录，索引通常具有明显优势。

这里就出现了数据库内部一个非常重要的组件：查询优化器（Query Optimizer）。

PostgreSQL 的优化器会根据表的统计信息、索引信息、查询条件和成本模型，估算不同执行路径的代价，然后选择它认为更合适的执行计划。

需要强调的是，优化器通常不是把所有理论上可能的执行方案全部实际运行一遍，再选择最快的那个。

它依靠统计信息和成本估算进行规划。对于复杂查询，还需要采用不同的搜索策略，控制规划本身的开销。

这也解释了一个很多 DBA 都遇到过的现象：明明 SQL 没有改变，执行计划却发生了变化。

因为表中的数据量、数据分布、统计信息、索引结构乃至优化器参数，都可能发生变化。

SQL 描述的是我们想要什么，而执行计划描述的是数据库准备怎样得到它。

这两者不是一回事。

## 三、执行计划：数据库准备采取的行动

既然优化器会选择执行方式，那么我们能不能看到它的选择？

可以。

PostgreSQL 提供了一个非常重要的命令：

```sql
EXPLAIN
SELECT * FROM users WHERE id = 100;
```

它可以展示数据库为这条 SQL 生成的执行计划。

如果选择顺序扫描，计划中可能出现：

```text
Seq Scan
```

如果选择普通索引扫描，则可能出现：

```text
Index Scan
```

还有其他可能，例如 Bitmap Heap Scan 或 Index Only Scan。实际选择取决于表结构、数据分布、查询条件和执行环境。

这里需要区分两个容易混淆的概念。

普通的 `EXPLAIN` 主要展示规划器生成的计划和估算信息，并不会真正执行这条 SELECT 查询。

而：

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE id = 100;
```

会实际执行查询，并记录运行过程中的部分统计信息。

其中，`ANALYZE` 让我们能够观察实际执行时间、返回行数以及节点执行次数等信息；`BUFFERS` 则展示执行过程中与缓冲区访问有关的统计数据。

这意味着，我们不必只依赖理论推测数据库的行为，而是可以通过实验观察。

不过，执行计划也不是数据库内部活动的完整录像。它主要展示执行器的计划节点及相关统计，并不会直接列出解析器的全部工作、每一次内部函数调用，或者所有操作系统层面的 I/O。

我们需要知道工具能够证明什么，也需要知道它不能证明什么。

## 四、动手实验：让 PostgreSQL 自己告诉我们

接下来，我们设计一个简单实验。

目的不是测试 PostgreSQL 的极限性能，而是观察一个最基本的问题：**当数据量发生变化、索引出现以后，数据库会怎样选择查询路径？**

建议使用 PostgreSQL 16 或更新的受支持版本进行实验，并记录实际版本。下面的 SQL 使用了常见的 PostgreSQL 功能，实验应在独立测试数据库中运行。

首先创建一张用户表：

```sql
DROP TABLE IF EXISTS users;

CREATE TABLE users (
    id INTEGER,
    username TEXT,
    email TEXT
);
```

我们暂时不设置主键，因为 PostgreSQL 在创建主键时通常会自动创建支持该约束的唯一 B-Tree 索引。为了观察没有索引时的行为，这里先使用普通字段。

插入 100 条数据：

```sql
INSERT INTO users (id, username, email)
SELECT
    i,
    'user_' || i,
    'user_' || i || '@example.com'
FROM generate_series(1, 100) AS i;

ANALYZE users;
```

然后执行：

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE id = 100;
```

在没有索引的情况下，PostgreSQL 通常会选择顺序扫描。

现在我们增加数据量：

```sql
INSERT INTO users (id, username, email)
SELECT
    i,
    'user_' || i,
    'user_' || i || '@example.com'
FROM generate_series(101, 1000000) AS i;

ANALYZE users;
```

再次执行相同的查询：

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE id = 100;
```

此时表中已有一百万条记录，但仍然没有索引。数据库通常仍需要扫描数据页，检查记录是否满足条件。

接下来创建索引：

```sql
CREATE INDEX idx_users_id
ON users(id);

ANALYZE users;
```

再次执行同样的查询：

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE id = 100;
```

这时，优化器通常会倾向于使用索引扫描，因为查询只需要返回极少量记录，而索引能够显著缩小需要访问的数据范围。

不过，具体执行计划需要以真实运行结果为准，不能仅凭存在索引就断言优化器一定会使用它。

为了让实验更有意义，我们还可以增加一条查询：

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE id <= 900000;
```

这条查询可能返回表中绝大多数记录。

即使已经创建了索引，PostgreSQL 仍然可能选择顺序扫描，因为通过索引访问大量数据行，并不一定比顺序读取整张表更划算。

这里我们只给出了实验方法和基于成本模型的预期现象，并没有把尚未实际运行的执行计划伪装成测试结果。

读者可以在自己的 PostgreSQL 环境中执行这些语句，观察计划节点、实际行数、耗时以及缓冲区统计的变化。

这个实验虽然简单，却揭示了数据库非常重要的设计思想：

**索引不是一个要求数据库必须使用的指令，而是优化器可以选择的一条访问路径。**

## 五、执行器究竟在做什么？

当优化器选定执行计划以后，工作就交给执行器（Executor）。

执行器负责按照计划节点组织实际的数据处理。

我们仍然以最初的 SQL 为例：

```sql
SELECT * FROM users WHERE id = 100;
```

假设优化器选择了普通 B-Tree 索引扫描。

执行器会通过相应的索引访问机制，在索引中查找 `id = 100` 对应的条目。

对于普通的 PostgreSQL B-Tree 索引，索引条目通常包含键值以及指向堆表记录位置的 TID（Tuple Identifier）。

这个 TID 可以帮助数据库定位到对应的数据页和页内记录位置。

这里与某些数据库的存储设计有所不同。

例如，MySQL InnoDB 的聚簇索引把表记录组织在主键 B+Tree 的叶子页中，而 PostgreSQL 常规表通常采用 Heap 存储，索引与表数据分别组织。

因此，对于普通的 PostgreSQL Index Scan，数据库通常需要根据索引中的位置引用，再访问 Heap 中的相应记录。

当然，PostgreSQL 也支持 Index Only Scan，在满足一定条件时可以减少对 Heap 的访问。这个机制还涉及可见性映射（Visibility Map），我们以后会专门讨论。

现在先记住一点：

索引负责帮助数据库缩小查找范围，但找到索引条目，并不总意味着已经拿到了可以直接返回给用户的最终结果。

## 六、数据究竟从哪里来？

我们已经知道，执行器可以通过索引定位到数据页。

但接下来又出现一个问题。

这个数据页是在磁盘上，还是在内存中？

如果每次查询都必须从磁盘读取数据，数据库的性能显然会受到很大限制。

因此，PostgreSQL 使用一块共享内存区域来缓存数据库页面，其中最重要的部分之一就是 Shared Buffers。

可以把它理解为数据库自己维护的一套数据页缓存。

当执行器需要访问某个页面时，相关存储访问机制会检查这个页面是否已经位于共享缓冲区中。

如果页面已经存在，就可以直接使用内存中的缓存页面。

如果不存在，就需要把相应页面读入共享缓冲区。这个读取过程还可能受到操作系统文件缓存的影响，因此并不意味着每次缓存未命中都会产生真实的物理磁盘读取。

这也是为什么同一条 SQL，第一次执行和第二次执行的耗时可能不同。

第一次查询可能需要读取一些尚未缓存的数据页，而第二次执行时，这些页面可能已经存在于缓存中。

不过，我们不能简单地把这种现象理解成“第一次读磁盘，第二次读内存”。

PostgreSQL 的 Shared Buffers 和操作系统页缓存是不同层次的缓存。仅仅观察两次 SQL 的执行时间，还不足以证明数据究竟来自哪一层。

回到前面的实验：

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE id = 100;
```

我们可能看到 `shared hit`、`shared read` 等统计字段。

`shared hit` 表示相关页面访问命中了 PostgreSQL 的共享缓冲区。

`shared read` 表示 PostgreSQL 需要把页面读入共享缓冲区，但它本身并不能证明底层一定发生了物理磁盘 I/O，因为操作系统可能已经缓存了文件内容。

另外，`BUFFERS` 统计的是缓冲区访问活动，而不是查询涉及多少个互不重复的数据页。

理解这些区别，对实际分析 PostgreSQL 性能非常重要。

一个看起来简单的查询，其性能可能受到索引结构、数据页布局、缓存命中情况和底层存储系统等多种因素影响。

而这些因素，恰好构成了数据库内部结构的重要部分。

## 七、找到记录以后，为什么还不能立即返回？

到这里，我们似乎已经完成了查询。

SQL 被解析，优化器选择执行计划，执行器找到目标数据页，并定位到了记录。

但 PostgreSQL 还有一项非常重要的工作：判断这条记录是否对当前事务可见。

为什么需要这个步骤？

假设有两个事务同时操作同一条记录。

事务 A 正在修改某个用户的信息，但还没有提交。此时事务 B 查询这个用户，究竟应该看到修改之前的数据，还是修改之后的数据？

如果数据库不加控制地返回当前物理存储中的内容，就可能让一个事务看到另一个事务尚未提交的修改。

为了处理并发访问，PostgreSQL 使用多版本并发控制，也就是 MVCC（Multi-Version Concurrency Control）。

在 PostgreSQL 的 Heap Tuple 中，存在与事务版本管理有关的元数据，例如 `xmin` 和 `xmax`。

它们并不是简单的创建时间和删除时间，而是与插入、删除、更新以及行锁定等操作有关的事务标识信息。数据库还需要结合事务状态、快照以及其他元数据判断可见性。

因此，即使数据库已经通过索引找到了某条记录，也仍然需要确定它是否属于当前事务可以看到的版本。

这个机制让 PostgreSQL 能够在一定条件下实现读写并发，而不必让普通查询总是等待正在修改数据的事务。

当然，MVCC 也不是没有代价。

旧版本记录不会因为新版本出现就自动从物理存储中消失。PostgreSQL 需要依靠 VACUUM 等机制清理不再需要的旧版本，并维护相关空间。

这也是 PostgreSQL 与 Oracle、MySQL InnoDB 在内部实现上值得深入比较的地方。

Oracle 主要通过 Undo 信息构造一致性读所需的历史版本；InnoDB 也依赖 Undo Log 和 Read View 等机制；PostgreSQL 则主要把行版本保留在 Heap 中，并通过事务可见性规则和 VACUUM 管理版本生命周期。

三者都需要解决并发读写和一致性问题，但内部结构并不相同。

对于第一篇，我们暂时不深入讨论这些细节。

只需要理解一个事实：**数据库找到了一条物理记录，不等于这条记录一定可以返回给当前查询。**

这也是数据库与普通文件读取之间一个非常重要的区别。

## 八、把整个过程重新连接起来

现在，我们再看最初那条 SQL：

```sql
SELECT * FROM users WHERE id = 100;
```

它已经不再只是一句简单的查询语句。

在典型的 PostgreSQL 查询处理中，它需要经历几个相互关联的阶段。

首先，数据库通过解析和语义分析理解 SQL，确认相关对象和表达式，并完成必要的查询重写。

随后，优化器根据可用的访问路径、统计信息和成本估算生成执行计划。

执行器按照计划工作，可能通过顺序扫描，也可能通过索引定位所需记录。

访问数据时，数据库会利用共享缓冲区管理页面读取。相关数据可能已经在 PostgreSQL 缓存中，也可能需要经过操作系统读取。

找到候选记录以后，还需要按照当前事务的可见性规则判断是否能够返回。

最后，执行器产生结果，PostgreSQL 通过客户端协议把结果发送给应用程序。

需要说明的是，这是一条典型简单查询的概念性路径，而不是所有 SQL 都必须严格经历的固定流程。

PostgreSQL 还支持预处理语句、扩展查询协议、不同的执行计划缓存行为，以及复杂得多的查询和执行机制。我们以后会逐步接触这些内容。

但从这条简单 SQL 出发，已经足以看出数据库内部的基本轮廓。

数据库并不是一个接收 SQL 然后直接读取文件的程序。

它是一套由多个子系统协同工作的复杂软件。

解析器负责理解请求，优化器负责选择策略，执行器负责组织操作，存储和缓冲区管理负责高效访问数据，并发控制机制负责维护事务可见性，日志与恢复机制则承担持久化和故障恢复的重要职责。

这些机制彼此独立，又相互影响。

一个查询为什么慢，可能不是 SQL 写得不好，而是统计信息不准确；可能不是索引缺失，而是数据分布发生了变化；可能不是磁盘性能不足，而是缓存访问模式不理想。

真正理解数据库，就不能只盯着某一个组件，而要理解整个系统如何协作。

## 九、为什么理解内部结构，对 DBA 如此重要？

对于普通开发者来说，数据库能够正确返回结果，很多时候就已经足够。

但对于 DBA，事情往往没有这么简单。

一条原本执行几十毫秒的 SQL，突然变成几十秒。

数据库 CPU 使用率突然升高，磁盘 I/O 却没有明显变化。

明明创建了索引，优化器却坚持使用顺序扫描。

同样一条查询，在测试环境很快，在生产环境却很慢。

这些现象背后，可能涉及完全不同的内部机制。

如果我们只记住一些经验性的优化规则，比如“查询慢就加索引”“定期更新统计信息”“尽量避免全表扫描”，就很容易在复杂场景中失去判断依据。

因为这些经验都有适用条件。

顺序扫描并不一定慢，索引扫描也不一定快。缓存命中率高不代表整个系统没有性能问题，执行计划相同也不代表实际执行成本一定相同。

只有理解数据库内部的工作过程，我们才能从观察到的现象出发，逐步缩小问题范围，找到真正的原因。

这也是为什么我认为，学习数据库不能只停留在 SQL、参数配置和日常运维操作上。

那些知识当然重要，但它们只是数据库呈现在外部的操作界面。

数据库真正值得研究的，是隐藏在这些操作背后的结构。

## 十、接下来，我们要拆开这台机器

第一篇文章，我们沿着一条 SQL 的执行过程，粗略走过了 PostgreSQL 内部的几个重要区域。

但实际上，我们只是刚刚打开数据库的大门。

为什么数据库要把数据组织成一个个 Page？为什么 B-Tree 能够高效定位数据？为什么优化器需要统计信息？为什么 PostgreSQL 要保留旧版本记录？为什么数据修改以后还需要 WAL？为什么数据库必须定期执行 Checkpoint？

这些问题看似分散，实际上都与同一个目标有关：在有限的计算、内存和存储资源下，尽可能高效、可靠地管理不断变化的数据。

而且这些目标之间并不总是协调的。

提高写入性能，可能增加故障恢复的复杂性；减少存储空间，可能增加计算开销；提高并发能力，可能带来更多版本管理成本；让优化器选择更复杂的执行路径，也意味着规划本身需要付出代价。

数据库设计从来不是简单地追求某一个指标的最大化，而是在不同约束之间不断寻找平衡。

接下来的文章，我们会从这张内部结构图出发，逐步深入存储、索引、查询优化、事务、日志和恢复等机制。

我们会以 PostgreSQL 为主要实验平台，尽可能通过可以复现的 SQL、执行计划、系统指标以及必要的源码分析，理解每一个机制为什么存在，又是如何工作的。

同时，也会结合 Oracle 和 MySQL 的不同实现，看看面对相似的问题，不同数据库为什么会作出不同的设计选择。

最终希望达到的，并不是记住更多数据库术语，而是形成一种理解数据库的方法。

当我们再次看到一条 SQL 时，脑海中不再只有查询条件和返回结果，而是能够逐渐想象出数据库内部正在发生什么。

**真正理解一个复杂系统，往往始于看清一件最普通的事情，是如何发生的。**

而我们要研究的第一件事，就是一条 SQL。
